# Контракты модулей

JavaScript-модули браузера без сборки. Тесты Node.js используют ESM. UI и сообщения пользователю — на русском языке.

## Калькулятор (`src/calculator.js`)

Экспорты: `parseNumber(value)`, `formatMoney(value, currency='RUB')`, `validateConfig(raw)`, `validateMetalPrices(raw)`, `calculateQuote(rows, config)`.

`validateConfig` нормализует `{version,currency,coatings:[{code,name}],formulaMode,rounding,calculationVersion:2}`. Режимы — `catalog`/`excel`, округление — `unit`/`line`. Уникальные коды покрытий обязательны; старый `coefficient` игнорируется. Поле `prices_per_kg` не загружает цены через настройки покрытий. `version` справочника не определяет формулу. Валюта по умолчанию `RUB`.

`validateMetalPrices` принимает отдельный `{version,currency,prices_per_kg}`. Ключи — положительные безопасные целые ID товаров, значения — конечные неотрицательные цены за кг. Возвращает нормализованный справочник; пустые и некорректные данные отклоняются. Цена отсутствующего товара не заменяется нулём.

Общие поля строки: `{id,productId,productName,currency,quantity,coatingCode,k1,k2,k3,executionTerm,ralColor}`. Для выбранной вариации дополнительно сохраняются `isVariation:true`, `parentProductId` и необязательный `parentProductName`. Эти поля описывают связь; расчёт, цены металла и CRM используют собственный `productId` вариации. Каталог дополнительно использует `basePrice`; Excel — `pricePerKg`, `weight`, `fasteners`.

```text
catalog: unit = basePrice × k1 × k2 × k3
excel:   unit = pricePerKg × weight × k1 × k2 × k3 + fasteners
lineTotal = unit × quantity
```

Вес и метизы относятся к единице изделия. К3 вводится вручную; покрытие служит только наименованием. `ralColor` — необязательный текст до 100 символов, сохраняемый для строки; `formatCoating` добавляет `RAL <цвет>` к наименованию окраски, не изменяя формулу. `supportsRal:true` разрешает ввод цвета для произвольного покрытия; стандартные варианты окраски определяются и по коду/наименованию. `extraCoating` и `delivery` не участвуют в новой формуле. `executionTerm` — текст, сохраняемый и передаваемый в документ.

Числа допускают десятичную запятую. Пустой и нечисловой ввод, бесконечность и неверная валюта ошибочны. К1/К2/К3 допускают ноль и отрицательные значения. Количество и вес положительны; цены и метизы неотрицательны. В каталоге вес не проверяется, в Excel базовая цена каталога не заменяет стоимость металла.

Деньги округляются до двух знаков. `unit`: сначала цена единицы, затем произведение на количество. `line`: сумма строки из неокруглённой цены; отображаемая цена округляется отдельно. Результат: `{rows:[{...row,unitPrice,lineTotal,valid,errors}],total,quantity,valid,errors}`. При неверной строке `valid:false`, готовый итог отсутствует: частичный расчёт не считается предложением.

## REST-адаптер (`src/bitrix.js`)

`BitrixAdapter` использует официальный BX24 SDK и авторизацию установленного приложения. Основные методы:

| Метод | Результат/назначение |
| --- | --- |
| `init()` | `{connected,dealId}` |
| `call(method,params)` | Вызов SDK с обработкой ошибок |
| `loadDeal(id)` | Сделка, клиент, валюта и существующие товарные строки |
| `searchProducts(query)`, `getProduct(id)` | Товары с подтверждённой базовой ценой и валютой |
| `loadDiskJson(fileId)` | `{data,fileId,version,name}`; общий способ чтения обоих справочников |
| `registerPlacement(title)` | Явная регистрация вкладки |
| `loadHistory(folderId,dealId)` | Снимки конкретной сделки |
| `saveSnapshot(folderId,snapshot)` | Новый файл `{fileId,name}` |
| `applyToDeal(dealId,snapshot,expectedFingerprint)` | Замена строк с проверкой состояния и чтением результата |
| `listDocumentTemplates(dealId)` | Зарегистрированные доступные шаблоны |
| `createQuoteDocument(dealId,templateId,snapshot)` | Создание CRM-документа из снимка |
| `getResponsibleManager(dealId)` | Подпись текущего ответственного: имя, должность, рабочий телефон |
| `getQuoteDocument(id)` | Обновление состояния уже созданного документа |

`init()` ждёт ответ портала до 15 секунд, подхватывает SDK, загрузившийся после создания адаптера, и сохраняет безопасную причину сбоя в `connectionError`. Повторная попытка не зависит от позднего callback предыдущей. Сам адаптер при инициализации не вызывает REST; интерфейс отдельно проверяет `app.info`, прежде чем подтвердить соединение.

Списки обходятся с пагинацией. Первый запрос не содержит `start=0`: SDK сам передаёт следующий курсор через `Result.next()`, а явный ноль в `data` официального SDK может остаться в клонированном запросе и перекрыть следующий `start`. Возвращённый `answer.next` должен увеличиваться; повторный или убывающий курсор прекращает чтение с `PAGINATION_STALLED`. Базовая цена каталога запрашивается отдельно через `catalog.price.list` с базовой группой цен; применяется проверенный legacy fallback. Отсутствие цены не подменяется нулём. Поиск вариаций читает `catalog.product.sku.list` (массив `units`) и `catalog.product.offer.list` в связанном инфоблоке `productIblockId`. Поиск по названию основного товара добавляет его вариации даже при другом наименовании исполнения; поиск по ID основного товара возвращает только его активные вариации. `getProduct(id)` по-прежнему подтверждает только конкретную продаваемую позицию, основной товар SKU записать в сделку нельзя. Связь `parentId` принимается числом либо объектом `{value,valueId}`; при раскрытии проверяется принадлежность вариации запрошенному основному товару. Повторные совпадения удаляются по ID. Поля каталога не записываются. Чтение существующих товаров сделки сохраняет их договорные цены и налоговые параметры.

Снимки имеют уникальные имена `yuzm-kp-deal-{dealId}-{variantId}-v{version}-{snapshotId}.json`. История считается общей только при работающей загрузке и чтении папки. Ошибки не должны раскрывать токены или URL с авторизацией.

`applyToDeal` заменяет весь набор строк после отдельного подтверждения в UI. Экспорт `fingerprintRows(rows)` нужен для сравнения со строками, показанными пользователю. Проверка до записи обнаруживает изменившуюся сделку; чтение после записи проверяет результат. Это не транзакция и не блокировка другого менеджера. Для CRM цена округляется до умножения на количество.

## Генератор документов

Методы адаптера используют `crm.documentgenerator.template.list`, `crm.documentgenerator.document.add` и `crm.documentgenerator.document.get`. Результат документа: `{id,title,downloadUrl,pdfUrl,publicUrl}`; ссылки появляются только при наличии в ответе, PDF может быть ещё не готов.

В `document.add` передаётся ID сделки и зарегистрированный `templateId`. Товарная таблица создаётся из сохранённого КП через массив `KpItems`, `ArrayDataProvider` и дескрипторы переопределения меток. Сопоставление исходному пользовательскому DOCX:

- `ProductsIndex`, `ProductsProductName`, `ProductsProductQuantity` — номер, название и количество строки.
- `ProductsProductPriceBrutto`, `ProductsProductPriceBruttoSum` — расчётная цена и сумма строки.
- `YuzmCoating`, `YuzmDeliveryPeriod` — наименование покрытия и срок исполнения.
- `TotalSum`, `RequisiteRqCompanyName` — итог и клиент сохранённого КП.

Содержимое `data/templates/kp-yuzm-bitrix24.docx` не изменяется. После проверки снимка и шаблона генерация обязательно вызывает `applyToDeal` с составом этой версии и отпечатком актуальных строк. Создание документа выполняется только после успешного повторного чтения товаров. Ошибка записи, конфликт или неподтверждённое чтение блокируют `document.add`. Если после подтверждённого переноса генератор отказал, ошибка содержит `goodsTransferred:true`; отката и автоматического повтора нет. Обновление PDF запрашивает существующий ID, а не повторяет `document.add`.

`draft.documentFields` — объект конкретного варианта с разрешёнными текстовыми метками `YuzmPaymentTerms`, `YuzmFastenerTerms`, `YuzmDocumentsTerms`, `YuzmDeliveryTerms`, `YuzmValidityTerms`, `YuzmManagerPosition`, `YuzmManagerName`, `YuzmManagerPhone`. Сохранение копирует его в `snapshot.documentFields`, генерация использует значения снимка. Поля независимо копируются при дублировании варианта и восстанавливаются из локального состояния. Объект не создаёт связи с технической документацией или чертежами.

Предустановки оплаты 40/60, 50/50 и 100% предоплаты заполняют редактируемый текст `YuzmPaymentTerms`. Начальные условия — из предоставленного образца; должность, имя и телефон менеджера изначально пустые. Адрес доставки образца не подставляется из реквизитов сделки и должен редактироваться для соответствующего КП. Полные исходные формулировки приведены в [data-format.md](data-format.md).

## Состояние и интерфейс (`src/app.js`, `index.html`, `styles.css`)

`yuzmQuoteTemplateId` в общих настройках Bitrix24 — единый шаблон для всех пользователей данного приложения. `getQuoteTemplateId()` читает его через `app.option.get`; `setQuoteTemplateId(id)` требует `BX24.isAdmin()`, записывает `app.option.set` и подтверждает ID повторным чтением. Ошибка чтения блокирует генерацию, локальный запасной шаблон не используется. `documentTemplateId` в снимке фиксирует общий выбор на момент сохранения. Каждый вариант содержит отдельный реестр `documents:[{snapshotId,templateId,...doc,createdAt}]`. Обновление документа не меняет сохранённый снимок. Реестр сохраняется в локальных данных варианта; Диск хранит сами снимки, а не общий межбраузерный реестр ссылок.

Новые снимки — `schemaVersion:2` с К3, сроками, клиентом, `documentFields` и настройками расчёта. Старые снимки `schemaVersion:1` открываются со своими сохранёнными суммами. При миграции старого каталожного черновика прежний множитель покрытия переносится в К3. Старому черновику Excel нужны цена за кг и вес; прежние доплаты не возвращаются в формулу автоматически.

Настройки предоставляют отдельный импорт покрытий и цен металла с Диска или локального JSON. В строке есть покрытие, срок исполнения, количество и три коэффициента; в Excel дополнительно вес и метизы. Условия и менеджер редактируются в текущем варианте, выбор предустановки оплаты или крепежа заполняет расположенное рядом текстовое поле. Сохранение и предпросмотр не меняют сделку. Генерация документа обязательно переносит товары выбранной версии; отдельная кнопка применения позволяет перенести текущий расчёт без документа. Поле даты отгрузки и флаг нестандартной позиции отсутствуют в новых черновиках и снимках; исторические снимки не изменяются. Общий зарегистрированный шаблон выбирается администратором только в настройках и может быть изменён там же. Кнопка печати в предпросмотре отсутствует. Документ можно открыть, а поздний PDF — получить обновлением статуса.

Используются нативные диалоги и безопасный вывод текста. Классический загрузчик `src/sdk-loader.js` подключает BX24 с `https://api.bitrix24.tech/api/v1/` и, при неудаче, с `https://api.bitrix24.com/api/v1/`. Пока запрос не завершён, повторная попытка использует тот же запрос, чтобы поздняя загрузка не заменила уже инициализированный SDK. Приложение подключается через `<script type="module" src="src/app.js"></script>` и ждёт загрузчик перед вызовом `init()`.

Глобальный `YUZM_BX24` предоставляет `load()` и `diagnostics()`. Диагностика содержит только код состояния, официальный источник SDK, наличие фрейма и контекста как булевы значения, доступность SDK и протокол страницы. Интерфейс добавляет версию приложения, безопасный код соединения и булево `connected`. В блок не включаются токены, SID, ключи, сырые параметры фрейма, URL страницы или адрес портала.

## Ошибки поиска и диагностика REST

С версии 2.5.0 интерфейс использует `listCatalogEntries({refresh,onProgress})` — полный индекс названий и ID без цен. Он включает обычные товары и активные вариации, исключает основные товары SKU из выбираемых позиций и удаляет дубли по ID. Метаданные имеют `verified:false`; это не готовая расчётная строка. Связи с известными основными товарами добавляют `parentProductName` для поиска. Вариация с неизвестным основным товаром остаётся доступна по собственным названию и ID. Общий список не использует фильтры `parentId` / `@parentId` и не ограничен 500 позициями. Параллельные чтения объединяются; кэш существует только в памяти страницы. Кнопка обновления сбрасывает кэш каталога, вариаций и базового типа цены. Ошибочное чтение не считается готовым кэшем и может быть повторено.

Поиск выпадающего списка выполняется локально по собственному имени, имени известного основного товара или ID. При выборе вызывается `getProduct` для текущей цены и валюты выбранного ID. Только успешная проверка заменяет или добавляет строку; ошибка не меняет прежние строки и сохранённые версии. Основной товар SKU нельзя выбрать вместо вариации. Старый метод адаптера `searchProducts` сохранён для совместимости; его ценовая выдача сохраняет собственный предел 500, но интерфейс этим методом не пользуется. Раскрытие родителя в этом методе фильтрует общий список вариаций локально и не прерывается из-за посторонней вариации.

С версии 2.4.2 `searchProducts(query, {by})` поддерживает `name`, `id` и совместимый `auto` (по умолчанию для вызовов адаптера). В интерфейсе выбран `name`: цифры считаются частью наименования. `id` проверяет положительный целочисленный ID и раскрывает основной товар в его вариации. `auto` сохраняет прежнее поведение для вызовов без опций. Современным списочным методам поиск имени передаётся явным фильтром `"=%name":"%текст%"` для подстроки в любой позиции. Выбор режима и результаты не попадают в снимок КП. Изменение режима запускает новый поиск; поздние результаты старого запроса игнорируются.

С версии 2.4.1 `BitrixAdapter.diagnostics()` возвращает не более 20 записей `{method,state,pages,items,elapsed_ms,code?}`. С версии 2.4.2 добавлены проверенные числовые `total_items?` и `next_offset?` из серверного ответа. Это журнал REST-вызовов без параметров и ответов; `state` — `pending`, `success` или `error`. Приложение включает его в `rest_requests` диагностики подключения. Успешный REST-вызов с последующей ошибкой проверки данных остаётся `success` в журнале: текст ошибки проверки показывается в интерфейсе.

`_readProduct` переходит к другому типу товара только при известном отсутствии товара или метода. Пустой/нулевой код сам по себе не означает отсутствие товара: требуется известная формулировка сервера, которая заменяется собственным `PRODUCT_NOT_FOUND`. Отказы, лимиты и тайм-ауты сохраняются и не вызывают legacy-поиск. Некорректный ID в успешном ответе также останавливает поиск. При отсутствии ID `searchProducts` возвращает `[]`, а `getProduct` блокирует перенос неподтверждённого товара в сделку. Legacy-путь остаётся для порталов без всех трёх современных get-методов.

Старый метод `searchProducts` ограничивает ценовую выдачу 500 записями: превышение возвращает `CATALOG_SEARCH_TOO_BROAD`. С версии 2.5.0 интерфейс загружает полный индекс через `listCatalogEntries` без этого ограничения. Пустой запрос показывает все записи. Неизвестный формат необязательной связи `parentId` не угадывается и не блокирует вариацию: собственные ID, имя и цена проверяются отдельно, а имя основного товара добавляется только при известной корректной связи.

## Автозаполнение подписи

`getResponsibleManager(dealId)` возвращает `{dealId,userId,name,position,workPhone,phoneAvailable}` после проверки ID сделки и ровно одного пользователя с совпадающим ID. Он использует `ASSIGNED_BY_ID`, не `CREATED_BY_ID`, и вызывает только `crm.deal.get` и `user.get`. Приватные контактные поля не запрашиваются. Отсутствующее поле `WORK_PHONE` отличается от существующего пустого поля: первое подсказывает проверить `user_basic`, второе — вручную заполнить телефон.

`draft.managerOverrides` отмечает ручные изменения трёх полей подписи. Старые непустые поля черновиков считаются ручными. Автозаполнение обновляет только поля без отметки; явная кнопка заменяет подпись целевого варианта и снимает отметки. Новые варианты получают текущий профиль; дублирование копирует подпись и отметки независимо. Старые версии, восстановленные в черновик, и варианты из общей истории сохраняют всю подпись, включая намеренно пустые поля.

Запрос профиля привязан к области сделки и номеру запроса: поздний ответ другой сделки или после перехода в демо игнорируется. Ошибка профиля не меняет статус соединения с CRM. Сохранение и экспорт черновика ждут завершения первичного автозаполнения. Снимки хранят значения подписи в `documentFields`; генерация не читает профиль заново и добавляет разделяющий пробел между соседними полями должности и имени, не меняя снимок.

С версии 2.3.0 новый документ из любой сохранённой версии создаётся по текущему общему шаблону, повторно прочитанному с портала перед генерацией. Поле `documentTemplateId` в снимке остаётся сведением о выборе на момент сохранения и не управляет генерацией. Товары, цены, сроки, условия и подпись берутся из снимка. Уже созданные документы сохраняются со своими ID и шаблонами; после смены общего шаблона можно создать новый документ из той же версии.
