# Форматы данных пилота

Все справочники — JSON в UTF-8. На Диске Bitrix24 создайте два файла: связи и настройки покрытий. В приложении указываются ID **файлов**, не общедоступные ссылки и не ID папок. Для общей истории отдельно укажите ID папки. XLSX на этом этапе нужно преобразовать в описанный JSON: прямое чтение XLSX не реализовано.

## Связи: две таблицы в одном файле

[Пример связей](../data/relations.example.json) содержит массивы `product_drawings` и `drawing_kd`:

```json
{
  "version": "relations-2026-10-08-1",
  "product_drawings": [
    {
      "product_id": "16",
      "product_name": "НФГ-6,0-02",
      "drawing_id": "nfg6-02-r1",
      "drawing_name": "НФГ-6,0-02 · ред. 1",
      "drawing_file_id": "900001"
    }
  ],
  "drawing_kd": [
    {
      "drawing_id": "nfg6-02-r1",
      "kit_id": "kd-nfg6-02-r1",
      "kit_name": "Комплект КД НФГ-6,0-02",
      "file_id": "900006",
      "file_name": "Спецификация НФГ-6,0-02"
    }
  ]
}
```

| Поле | Значение |
| --- | --- |
| `version` | Версия справочника, меняется при обновлении содержимого |
| `product_id` | ID торгового товара/предложения в каталоге Bitrix24; ключ связи |
| `product_name` | Необязательное удобное название; не используется вместо ID |
| `drawing_id` | Внутренний устойчивый идентификатор чертежа и его редакции |
| `drawing_name` | Необязательное отображаемое обозначение |
| `drawing_file_id` | Необязательный ID файла чертежа на Диске |
| `kit_id`, `kit_name` | Идентификатор комплекта КД и необязательное название |
| `file_id`, `file_name` | Необязательный ID файла комплекта на Диске и его название |

Числовые ID принимаются, но внутри приложения приводятся к строкам. Один товар может иметь несколько чертежей; каждый записывается отдельной строкой `product_drawings`. В этом случае менеджер должен выбрать чертёж. Для нескольких файлов комплекта повторите строки `drawing_kd` с одинаковыми `drawing_id` и `kit_id` и различными `file_id`.

Пара `product_id + drawing_id` не должна дублироваться. Все чертежи из `drawing_kd` должны присутствовать в `product_drawings`. Обозначение и файл одного чертежа должны совпадать во всех связях, как и название одного комплекта. Некорректные и противоречивые данные отклоняются, чтобы не прикрепить случайную документацию.

Связи **не задают цену**, состав изделия и количество комплектующих. Для автоматического расчёта по спецификации понадобится отдельный согласованный формат состава и правила расчёта; их нельзя вывести из названий файлов.

## Покрытия и режим расчёта

[Пример настроек](../data/coatings.example.json):

```json
{
  "version": "coatings-1",
  "currency": "RUB",
  "formulaMode": "catalog",
  "rounding": "line",
  "coatings": [
    {"code": "none", "name": "Без покрытия", "coefficient": 1},
    {"code": "zinc", "name": "Горячее цинкование", "coefficient": 1.18},
    {"code": "paint", "name": "Окраска", "coefficient": 1.12}
  ]
}
```

`code` должен быть уникальным. `coefficient` — конечное числовое значение. `formulaMode` принимает `catalog` или `excel`; `rounding` — `line` или `unit`. Цена позиции и валюта настроек должны совпадать; автоматической конвертации валют нет.

| Режим | Формула цены единицы |
| --- | --- |
| `catalog` | `basePrice × coating.coefficient × k1 × k2` |
| `excel` | `(basePrice + fasteners + extraCoating + delivery) × k1 × k2` |

В `excel` покрытие не умножает цену повторно: его денежная составляющая вводится в `extraCoating`. `fasteners`, `extraCoating`, `delivery` — доплаты на единицу изделия. Вес отсутствует в обоих режимах. Поле `prices_per_kg` из исходного файла допускается для совместимости, но не участвует в расчёте.

При `line` округляется `rawUnit × quantity`; отображаемая цена единицы округляется отдельно. При `unit` сначала округляется цена единицы, затем её произведение на количество. Итог — сумма округлённых строк. Во всех случаях округление до двух десятичных знаков. Поэтому произведение отображаемой цены единицы на количество в режиме `line` иногда отличается от суммы строки на несколько копеек.

К1 и К2 допускают отрицательные значения и ноль. Ввод с десятичной запятой допустим. Пустое поле, бесконечность и нечисловой текст ошибочны; количество должно быть положительным, базовая цена и доплаты неотрицательными. При ошибке в строке КП нельзя считать готовым по частичному итогу.

## Демонстрационные данные

Товары `16`–`19`, документы `900001`–`900011`, названия и цены созданы для пилота. Файлы открываются как локальная демонстрационная заглушка. Это не данные вашего портала, даже если на нём случайно существует такой же ID. Замените все соответствия реальными ID до работы с реальными сделками.

Исходный файл пользователя сохранён без изменения в [prices.original.example.json](../data/prices.original.example.json). Его цинкование `1,15` и окраска `1,08` отличаются от макета. Демонстрационный файл использует коэффициенты макета `1,18` и `1,12`; справочники не объединяются скрыто.

## Варианты и версии КП

Редактируется черновик выбранного варианта. Сохранение создаёт новый снимок с собственным ID и номером версии; дальнейшие правки не должны менять предыдущий снимок. Снимок связывает ID сделки и варианта, строки, расчётные цены, выбор чертежей и использованные настройки/связи. Изменение справочника применяется к новым расчётам, не пересчитывая сохранённую историю.

JSON-снимки доступны для выгрузки. При общей истории приложение создаёт отдельные файлы:

```text
yuzm-kp-deal-{dealId}-{variantId}-v{version}-{snapshotId}.json
```

Папка истории не является секретным хранилищем: настройте права доступа на самом Диске. Не записывайте токены, пароли или ссылки с параметрами авторизации в справочники или снимки. Уникальные имена предотвращают перезапись файла приложением, но не заменяют централизованное назначение версий и блокировки для одновременной работы менеджеров.

Основной формат импорта — JSON. `data/relations.example.xlsx` содержит те же связи на двух листах для просмотра и подготовки данных; прямой импорт XLSX не реализован. Соответствия демонстрационные и не являются подтверждённой инженерной документацией.
