# Подключение к Bitrix24

Приложение использует официальный BX24 SDK и REST в авторизации установленного приложения. Ниже описана настройка; реальные вызовы на вашем портале при разработке не проверялись. Для приёмки нужны тестовая сделка, отдельная папка Диска и зарегистрированный шаблон генератора документов.

## Предварительные условия

- Администратор может создавать локальные приложения и регистрировать встраивания.
- В облачном Битрикс24 доступ к REST API активен по подписке Маркетплейс или в пробном режиме. Для постоянной работы в зоне ru нужны платный тариф и подписка. [Условия доступа к REST API](https://apidocs.bitrix24.ru/first-steps/access-to-rest-api.html).
- В коробке доступны REST-методы CRM, каталога, Диска, встраивания и CRM-генератора документов. Набор методов зависит от версии коробки и установленных модулей.
- Файлы приложения доступны по HTTPS из браузера менеджеров; политика портала разрешает встраивание.
- Приложению предоставлены права `crm`, `catalog`, `disk`, `placement` и `user_basic` (для автозаполнения подписи); у менеджера есть доступ к сделке, товарам, справочникам, папке истории и генератору документов.

Используется пространство `crm.documentgenerator.*`. Проверьте доступность этого API для приложения на вашей версии коробки. Входящий вебхук не создаёт вкладку и не заменяет контекст установленного приложения. Секреты в код и JSON не добавляйте. Вне портала приложение работает как отдельная локальная демонстрация.

## Размещение и установка

1. Разместите `index.html`, `index.php`, `install.html`, `install.php`, `styles.css`, `src/` и `data/` с сохранением относительных путей. Сборка не нужна. Для коробки используйте отдельный HTTPS-каталог на собственном PHP-сервере.
2. Для облачного Битрикс24 выберите «Статичное» и загрузите готовый `dist/yuzm-kp-bitrix.zip`: `index.html` находится в корне и идёт первым, рядом расположены CSS, JS и JSON приложения. [Прямая загрузка установочного ZIP](https://github.com/Keiner-kaka/BITRIXXX/raw/refs/tags/v2.3.0/dist/yuzm-kp-bitrix.zip). Начиная с версии 2.0.2 необязательный `install.html` исключён из этого ZIP: Битрикс завершает установку автоматически и открывает конструктор. Архив GitHub «Code → Download ZIP» или «Source code (zip)» помещает проект во внешнюю папку и не подходит для этой загрузки. Для собственного HTTPS-размещения используйте полный пакет `dist/yuzm-kp-prototype.zip`.
3. Обработчик приложения `https://your-host.example/kp/index.php` принимает POST Bitrix24 и передаёт в браузер только ID сделки. Статичный `index.html` подходит, если ваш хостинг поддерживает POST для этого адреса. Заголовки `X-Frame-Options` и CSP `frame-ancestors` должны разрешать фрейм вашего портала.
4. Отдельных обязательных действий в мастере установки нет. Для серверного размещения оставьте «Путь для первоначальной установки» пустым и выключите «Приложение само завершает установку»: приложение получит статус установленного автоматически. Полный пакет сохраняет `install.html` и `install.php` как необязательный вариант для установки с мастером; там `BX24.installFinish()` вызывается кнопкой после готовности SDK. Если существующая версия остановилась на серой кнопке, очистите первый путь и выключите эту опцию, сохраните карточку и нажмите «Переустановить». Основной путь обработчика с `index.html` или `index.php` сохраните. [Правила мастера установки](https://apidocs.bitrix24.ru/settings/app-installation/local-apps/installation-master.html).
5. Откройте настройки приложения и нажмите «Зарегистрировать вкладку сделки». Регистрация не запускается при каждом расчёте.

Пример регистрации с адресом вашего размещения:

```javascript
BX24.callMethod('placement.bind', {
  PLACEMENT: 'CRM_DEAL_DETAIL_TAB',
  HANDLER: 'https://your-host.example/kp/index.php',
  TITLE: 'Конструктор КП'
}, result => {
  if (result.error()) return;
  // Вкладка зарегистрирована для приложения.
});
```

После регистрации заново откройте тестовую сделку. ID берётся из параметров placement. При запуске вне карточки ID сделки можно указать в настройках и подключить её.

Официальные описания: [вкладка CRM](https://github.com/bitrix-tools/b24-rest-docs/blob/main/api-reference/widgets/crm/detail-tab.md), [placement.bind](https://github.com/bitrix-tools/b24-rest-docs/blob/main/api-reference/widgets/placement-bind.md), [SDK Bitrix24](https://api.bitrix24.tech/api/v1/).

## Если приложение открыто в портале, но не подключается

Приложение проверяет три отдельных этапа: загрузку официальной библиотеки BX24, получение контекста фрейма от портала и ответ REST-метода `app.info`. Видимое размещение страницы в интерфейсе само по себе не подтверждает передачу контекста. Подключение подтверждается после получения `INSTALLED:true`; отказ REST не выдаётся за отсутствие фрейма.

При ошибке нажмите «Повторить подключение». Повторная проверка доступна и в настройках. Скопируйте блок «Диагностика подключения» из раздела «Соединение с Битрикс24»; он не включает токены, SID, ключи, адрес портала, URL страницы или произвольный текст ошибок API.

- `FRAME_CONTEXT_MISSING` — фрейм есть, но портал не передал необходимый контекст. Откройте приложение штатной кнопкой из карточки интеграции; при повторной ошибке передайте диагностику поддержке портала.
- `SDK_LOAD_FAILED` / `SDK_LOAD_TIMEOUT` — загрузка библиотеки не удалась или ещё не завершилась. Проверьте доступ к `api.bitrix24.tech` и `api.bitrix24.com`, блокировщик браузера, затем повторите подключение.
- `SDK_CONTEXT_REJECTED` / `SDK_EXECUTION_FAILED` — файл загрузился, но SDK не стал доступен. Проверьте ошибки браузера без передачи секретов.
- `INIT_TIMEOUT` — библиотека загружена, но портал не ответил на запрос контекста за 15 секунд. Повторите подключение; при повторной ошибке проверьте запуск через фрейм установленного приложения.
- `INSTALL_NOT_FINISHED` — REST сообщил, что установка не завершена. Проверьте её режим в карточке и выполните «Переустановить».
- Код отказа REST, например `LICENSE_ERROR` или `ACCESS_DENIED`, — библиотека и контекст уже получены; проверьте доступ к REST API, тариф, подписку и права в соответствии с фактическим кодом.

Сбои загрузки SDK и отсутствие контекста не доказывают тарифное ограничение. Нельзя подставлять случайный SID, секрет приложения или токен, чтобы обойти передачу контекста.

## Два справочника на Диске

1. Подготовьте [coatings.example.json](../data/coatings.example.json): покрытия содержат коды, наименования и необязательный признак `supportsRal:true` для ввода цвета. Цена от покрытия или RAL автоматически не меняется. Загрузите файл на Диск и укажите его ID в поле справочника покрытий (`pricesFileId`, прежнее внутреннее имя настройки сохранено).
2. Подготовьте [metal-prices.example.json](../data/metal-prices.example.json): `prices_per_kg` сопоставляет ID реального товара и цену за кг. Загрузите отдельный файл на Диск и укажите его ID в поле цен металла.
3. Создайте папку истории и укажите `historyFolderId`, если нужны общие снимки КП. Без неё история остаётся локальной.
4. Загрузите каждый справочник соответствующим действием. Проверьте валюту и ID товаров перед расчётом.

Загрузка использует `disk.file.get` и адрес скачивания. Доступ по REST и скачивание из браузера — отдельные условия. Если скачивание блокирует CORS, настройте разрешённый origin на вашем сервере/Диске. Для проверки можно скачать файл средствами портала и выбрать его как локальный JSON. Локальный импорт не создаёт синхронизацию с Диском; обновлённый файл загружается повторно вручную.

Файл покрытий не изменяет цены металла. Для Excel необходимы цена за кг и вес единицы; отсутствие цены не заменяется нулём. Подробный формат — в [data-format.md](data-format.md).

Не отключайте TLS-проверку и не размещайте токен в URL вручную. Перед передачей диагностических сообщений удаляйте ссылки скачивания и параметры авторизации.

## Шаблон КП и REST-генератор

1. Возьмите исходный пользовательский [kp-yuzm-bitrix24.docx](../data/templates/kp-yuzm-bitrix24.docx). В проекте его содержимое сохранено без изменений.
2. Зарегистрируйте DOCX штатными средствами генератора документов Bitrix24. Разрешите использование шаблона для сделок и доступ нужным менеджерам. Приложение выбирает уже зарегистрированный шаблон; само не загружает DOCX на портал.
3. Под администратором откройте сделку и настройки приложения. В разделе «Документы КП в Битрикс24» выберите «Общий шаблон КП» из зарегистрированных и нажмите «Сохранить настройки». Выбор хранится в `app.option` на портале и действует для всех менеджеров этого установленного приложения, включая другие браузеры и сделки. Для смены шаблона повторите выбор и сохранение. Менеджеры видят общий выбор, изменить его может администратор. После обновления с 2.2.0 выберите шаблон один раз: прежние локальные настройки автоматически не публикуются. Дополнительный scope для `app.option` не требуется.
4. Заполните строки, покрытия, К3 и текстовые сроки исполнения. В текущем варианте выберите условие оплаты 40/60, 50/50 или 100% предоплаты; при необходимости отредактируйте предложенный текст. Проверьте остальные условия и заполните имя, должность и телефон менеджера. Для окраски заполните номер RAL; для метизов выберите одну из трёх предустановок и при необходимости исправьте текст. Сохраните версию и создайте документ из выбранной версии: её товары обязательно заменят все товары сделки перед генерацией, без отдельного подтверждения.
5. Проверьте готовый DOCX и PDF на тестовой сделке, особенно повторение товарных строк, наименования покрытий, сроки и итог.

Список шаблонов читается через `crm.documentgenerator.template.list`; создание — через `crm.documentgenerator.document.add`; состояние готового документа — через `crm.documentgenerator.document.get`. Создание связано с ID сделки, но значения товарной таблицы берутся из сохранённого снимка КП. Приложение передаёт `KpItems` через `ArrayDataProvider` и переопределяет существующие метки таблицы, включая `{YuzmCoating}` и `{YuzmDeliveryPeriod}`. Полное соответствие меток приведено в [data-format.md](data-format.md).

Условия и поля менеджера принадлежат черновику конкретного варианта (`draft.documentFields`) и копируются в снимок. Их изменение в одном варианте не меняет другой вариант или сохранённую версию. Начальные условия взяты из предоставленного образца, включая доставку в г. Краснодар, Ставропольская, 19 силами поставщика. Этот адрес не определяется по сделке автоматически: отредактируйте его для соответствующего клиента.

Генерация PDF может завершиться после создания DOCX. Обновите статус существующего документа: приложение запрашивает его по ID и показывает появившуюся ссылку, не создавая повторный документ. При недоступном методе, шаблоне или результате требуется проверить модуль и права портала; ошибка не означает успешную генерацию.

Записи о созданных документах и их ссылках хранятся отдельно от неизменяемых снимков в данных варианта текущего браузера. Общая папка снимков не обеспечивает общий реестр этих ссылок между браузерами; сами документы доступны в CRM в пределах прав пользователя.

## Каталог и запись в сделку

Приложение читает торговое наименование и подтверждённую базовую цену каталога. Производственное название не является условием выбора товара. В каталожном режиме вес не нужен; в Excel вес вводится для единицы изделия. Автоматическая конвертация валют не выполняется. Если версия коробки или тип SKU не поддерживает нужные данные, приложение показывает ошибку вместо использования случайной цены.

Сохранение версии и предпросмотр не меняют товары сделки. Создание документа **обязательно заменяет весь текущий набор товарных строк сделки** выбранной сохранённой версией, без отдельного подтверждения. Перед записью и после неё приложение читает товары и проверяет состав. Отдельная кнопка «В товары сделки» позволяет перенести текущий расчёт без документа, с подтверждением замены. Повторная запись заменяет строки и не добавляет дубликаты.

Если другой менеджер изменил товары до применения, обновите данные и проверьте состав заново. REST не предоставляет общей транзакции для товарных строк и суммы сделки: проверка до/после не блокирует изменения другого пользователя во время записи.

Существующие товары сделки могут содержать договорные цены. Их чтение не означает равенство актуальным базовым ценам каталога. Перед применением проверьте сумму, скидки, налоги и автоматизации сделки; портал может применять дополнительные правила. Для CRM используется округление цены единицы, поскольку товарная строка хранит именно её.

## Общая история

При настроенной папке приложение читает JSON-снимки сделки и сохраняет новые отдельными файлами. Наличие ID папки не гарантирует доступ: загрузка и скачивание должны работать с правами менеджера. Ошибка Диска не подтверждает общую запись; локальную копию можно выгрузить отдельно.

Приложение не перезаписывает старые версии, но пользователи с соответствующими правами могут менять файлы Диска. Проверьте, что второй менеджер видит сохранённый снимок, а пользователь без прав не получает его данные. При одновременном сохранении номера версий могут совпадать; уникальные ID снимков предотвращают перезапись файлов.

Сценарии приёмки после установки перечислены в [validation.md](validation.md). Серверная защита расчётов, бизнес-согласование и автодобавление комплектующих потребуют отдельного этапа.

При создании документа сначала проверяются снимок и доступность шаблона, затем состав переносится в сделку с проверкой до и после записи. Отказ CRM или изменившаяся сделка останавливают генерацию. После успешного переноса отказ генератора не откатывает товары; приложение сообщает об этом. Предпросмотр, сохранение версии и обновление PDF товары не меняют.

## Подпись ответственного за сделку

Добавьте в настройках прав приложения **«Пользователи (базовый) — user_basic»**, сохраните карточку и заново откройте приложение. `user_brief` не возвращает рабочий телефон. Полный `user` также подходит, но базового уровня достаточно: профиль только читается. [Различия уровней доступа](https://apidocs.bitrix24.ru/api-reference/user/user-scope.html).

Приложение читает `ASSIGNED_BY_ID` сделки и запрашивает `user.get` с фильтром по этому ID и выборкой только `ID`, `NAME`, `LAST_NAME`, `WORK_POSITION`, `WORK_PHONE`. Создатель сделки, текущий пользователь приложения, личный и мобильный телефоны не участвуют в подстановке. Имя и фамилия соединяются пробелом; должность и рабочий телефон берутся как текст из профиля.

При открытии сделки и создании нового варианта подпись заполняется автоматически. Ручная правка любого поля, включая очистку, сохраняется в конкретном варианте и не перезаписывается автоматически. Кнопка «Подставить данные ответственного» получает свежий профиль и заменяет подпись выбранного черновика. Если телефон в профиле пуст, его вводят вручную. Недостаточные права или недоступный профиль показывают сообщение и не блокируют расчёт или ручное заполнение. Во время первичного чтения профиля сохранение версии ожидает завершения запроса.

Подпись входит в `snapshot.documentFields`: генерация старой версии использует сохранённые данные, даже если ответственный или его профиль изменились. Восстановление версии в черновик и восстановление варианта из общей истории сохраняют исходную подпись до явного заполнения из профиля. В документ передаются прежние метки `YuzmManagerPosition`, `YuzmManagerName`, `YuzmManagerPhone`. Между должностью и именем добавляется пробел, если в тексте должности ещё нет завершающего пробельного символа; DOCX не меняется.

С версии 2.3.0 новый документ из любой сохранённой версии создаётся по текущему общему шаблону, повторно прочитанному с портала перед генерацией. Поле `documentTemplateId` в снимке остаётся сведением о выборе на момент сохранения и не управляет генерацией. Товары, цены, сроки, условия и подпись берутся из снимка. Уже созданные документы сохраняются со своими ID и шаблонами; после смены общего шаблона можно создать новый документ из той же версии.
