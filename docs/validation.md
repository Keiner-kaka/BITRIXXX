# Проверка обновления

Автоматические проверки выполняются локально на демонстрационных данных и имитации BX24. Они не подтверждают доступность методов, права или успешную генерацию на рабочем портале Bitrix24.

Для версии 2.0.0 прошли `npm test` (все три файла проверок), `npm run check`, 20 браузерных проверок интерфейса и 14 браузерных проверок с имитацией Bitrix24. Исходный DOCX в пакете совпадает с присланным файлом по SHA-256. Рабочий портал не проверялся.

Версия 2.0.1 добавляет отдельный статичный установочный ZIP. Сборка проверяет `index.html` в корне первым файлом, переносимые ZIP-заголовки, все runtime-ресурсы и SHA-256 полного пакета. Приложение дополнительно запускается из распакованного статичного архива в Chromium, чтобы проверить загрузку модулей, JSON и интерфейса. Расчёт и REST-код относительно 2.0.0 не изменены.

Версия 2.0.2 исключает необязательный `install.html` из статичного установочного ZIP, чтобы Битрикс открывал конструктор автоматически. Сборка проверяет отсутствие мастера и наличие всех ресурсов; полный пакет сохраняет оба варианта установки. Из распакованного ZIP проверены запуск в Chromium и 14 сценариев с имитацией Bitrix24. Дополнительно старый мастер проверен с официальной библиотекой BX24 в тестовом фрейме: при получении контекста кнопка активируется и отправляет сигнал завершения установки. Завершение установки на рабочем портале требует отдельной проверки.

Для версии 2.1.0 прошли все три файла Node-проверок, проверка синтаксиса, 23 браузерных сценария интерфейса, 18 сценариев с имитацией Bitrix24 и 7 сценариев подключения. Последние используют актуальную официальную библиотеку BX24 и тестовый фрейм портала: проверены резервный сервер SDK, ответ контекста через 4 секунды, отсутствие контекста во фрейме, восстановление после сетевого сбоя, сохранение черновика при повторной попытке, отказ REST по лицензии, незавершённая установка, поздняя загрузка без второго экземпляра SDK и отсутствие секретов в диагностике. На рабочем портале подключение не проверялось.

## Локальные команды

Node.js 20+:

```bash
npm test
npm run check
```

При установленном Python Playwright и Chromium, с HTTP-сервером приложения на порту 8080:

```bash
python3 tests/browser_smoke.py
python3 tests/browser_bitrix.py
curl -fsSL https://api.bitrix24.tech/api/v1/ -o /tmp/yuzm-bx24-sdk.js
python3 tests/browser_connection.py
```

Проверки расчёта охватывают обе формулы с К3, положение метизов после коэффициентов, вес единицы, десятичные значения и оба способа округления. Отдельно проверяются справочники покрытий и цен металла, валюты и блокировка неготового Excel-расчёта при отсутствующей цене. Проверено, что старый коэффициент покрытия не влияет на новый расчёт.

Проверки адаптера с имитацией REST охватывают пагинацию каталога и шаблонов, чтение Диска, снимки истории, замену и повторное чтение строк сделки, контроль конкурентных изменений и безопасные ошибки. Для генератора проверяются значения из сохранённого КП, дескрипторы таблицы исходного DOCX, обязательный перенос товаров перед генерацией, блокировка создания при отказе CRM, конфликте или неподтверждённом повторном чтении и получение PDF по ID ранее созданного документа.

Проверки браузера охватывают ввод трёх коэффициентов и сроков, переключение режимов, отдельный импорт справочников, варианты, неизменяемые версии и восстановление после перезагрузки. Проверяются выбор зарегистрированного шаблона, предустановки и ручная правка оплаты, поля менеджера, независимость условий вариантов, ссылки документа, локальное хранение реестра, сохранение старых архивных сумм и миграция черновиков. Эти сценарии не заменяют просмотр результата на портале.

## Приёмка на тестовом портале

1. Откройте вкладку из тестовой сделки: проверьте ID сделки, клиента и валюту.
2. Выберите реальные товары каталога: базовая цена должна совпадать с каталогом; демонстрационные ID не используйте как подтверждённые данные портала.
3. Загрузите отдельные файлы покрытий и цен металла с Диска. Проверьте наименования, ID, цену за кг и валюту. Проверьте локальный импорт, отсутствие цены и запрет доступа к файлу.
4. В каталоге проверьте `basePrice × К1 × К2 × К3`. В Excel проверьте `(pricePerKg × weight × К1 × К2 × К3 + fasteners) × quantity`. Вес и метизы должны относиться к одной единице; доставка и прежняя доплата покрытия не должны попадать в формулу.
5. Заполните разные сроки исполнения у двух строк. Проверьте варианты оплаты 40/60, 50/50, 100% предоплаты и ручную правку текста; заполните менеджера и адрес доставки этого КП. Продублируйте вариант, измените его условия и перезагрузите страницу: условия исходного и нового вариантов должны остаться независимыми. Сохраните версии, измените текущий черновик и справочники: предыдущие суммы, покрытия, сроки, условия и менеджер должны сохраниться. Откройте старый снимок первого формата и сравните исходные значения.
6. Зарегистрируйте приложенный DOCX в генераторе документов. Загрузите доступные шаблоны, выберите шаблон по умолчанию и переопределение для отдельного варианта. Проверьте ошибку недоступного шаблона.
7. Создайте документ из сохранённой версии. В DOCX должны повториться только строки этого КП с правильными покрытиями, сроками, ценами и итогом, даже если текущие товары сделки отличаются. Проверьте условия и поля менеджера. Состав товаров сделки после генерации должен совпасть с выбранной сохранённой версией, включая цены и количество. Номер RAL должен отображаться в графе покрытия. Отказ CRM или ошибка проверки записи должны остановить создание документа.
8. Если PDF ещё не готов, обновите статус того же документа. Убедитесь, что появляется рабочая ссылка PDF и не создаётся второй документ. Проверьте открытие DOCX/PDF с правами менеджера.
9. При настроенной общей истории проверьте, что второй менеджер видит снимки КП на Диске. Реестр ссылок документов в приложении сохраняется в текущем браузере; общую доступность документов проверяйте средствами CRM и её правами.
10. Отдельно примените согласованную версию к тестовой сделке. Проверьте подтверждение замены, отсутствие дублей при повторе, фактические строки и сумму после записи. Изменение другим менеджером до применения должно обнаруживаться.

Проверьте CORS, встраивание, PHP-обработчики, права пользователей, налоги и автоматизации сделки в вашем окружении. Для CRM применяется округление цены единицы. Проверки до и после записи не блокируют конкурентное редактирование; для рабочего использования нужны согласованные правила управления изменениями.

В версии 2.1.0 дополнительно проверены оба покрытия с RAL, свободный текст цвета, сохранение номера при смене покрытия и перезагрузке, неизменность цены, совместимость старого справочника, три редактируемые предустановки крепежа и отсутствие даты отгрузки/признака нестандартной позиции.
