## Бизнес-логика

Формула сохранена:

```text
Цена единицы = (базовая цена + включённые метизы) × К1 × К2 × К3
Сумма строки = цена единицы × количество
```

Файлы `calculator.js`, `catalog.js`, `fasteners.js`, `manager.js`, `draft-store.js` совпадают с исходной Git-ревизией побайтно. SHA-256 неизменённого калькулятора: `2ae8450cc9ebe5d5e5ada28ab16700cf6bc3f7b1967af9f5ce0554d969bb2de7`.

К1/К2/К3 подписаны в строках и в админке. Доставка по К2 выделяется разницей между текущим итогом и расчётом тех же изделий штатным калькулятором с К2 = 1. Это сохраняет влияние скидки, покрытия, метизов, количества и действующего округления. Общая цена из-за выделения доставки не меняется.

Отдельная доставка оформляется обычной произвольной строкой с соответствующим флажком: уже входит в товары/итог и добавляется к стоимости доставки один раз. Отрицательная надбавка доставки блокирует сохранение с объяснением.

Масса учитывается отдельно от цены. При выборе товара используется уже читаемое свойство 112; для старых строк и работ нужно явно указать массу, включая 0. Итоговая масса — сумма массы единицы × количество.

Прежнее округление не переключается автоматически. Если округлённые цены единиц CRM дают иной итог, сохранение блокируется с предложением выбрать округление цены единицы. Дробный результат не теряется при записи в поле `integer`: требуется совместимое поле.

## Синхронизация и целостность

Сценарий записи: проверка настроек/первичных данных/товаров/сумм/размера JSON → предпросмотр и подтверждение полной замены → создание документа → проверка его принадлежности, номера и готовности DOCX → полная запись товаров → запись результатов/JSON → повторное чтение и проверка.

Каталожные строки используют `productId`, произвольные — `productName` и `productId = 0`. Если современный метод недоступен, используется прежний `crm.deal.productrows.set`. Результаты записываются только при сохранении КП, а не при редактировании формы.

В снимок входят ID сделки, документа и номер, время генерации, версия схемы/алгоритма, строки, исходные цены, количества, коэффициенты, метизы, доставка, масса, условия, фактически использованные тексты, суммы и SHA-256. Перед созданием документа проверяется лимит выбранного JSON-поля.

Результирующие поля не используются для расчётов. Их чтение после записи служит только проверке результата и обнаружению конкурентных изменений. Источник повторного расчёта — сохранённые исходные параметры.

Журнал операции хранится отдельно от черновика по порталу и ID сделки. При частичном сбое сохраняется ID уже созданного документа; повтор продолжает запись без копии. Неоднозначный ответ на создание блокирует автоматический повтор. Для привязки найденного документа проверяются сделка, шаблон и маркер операции. Web Locks исключает одновременную запись одной сделки из вкладок одного браузера.

При восстановлении проверяются JSON, схема, версия алгоритма, сделка, документ, контрольная сумма, внутреннее соответствие строк/текстов и суммы повторного расчёта. Текущий черновик заменяется только после подтверждения. При открытии приложения восстановления из CRM нет.

Сохраняется один актуальный снимок со статусом `generated`. Стадия сделки, согласование клиентом, производство и спецификации не изменяются. Ранее созданные документы остаются в истории CRM.

## Работа с текстами и Диском

JSON-файл поддерживает категории оплаты, доставки, метизов, документации и срока действия. Есть стабильные ID вариантов, подписи, текст по умолчанию и запрет/разрешение своего текста. Дополнительная категория с полем вида `Yuzm…Terms` не требует переписывать компоненты интерфейса.

Админка умеет выбрать файл из папки, открыть новый JSON, проверить структуру, показать варианты, опубликовать `disk.file.uploadVersion` с прежним ID и повторно прочитать результат. Существующие черновики сохраняют свои формулировки; менеджер выбирает новые варианты явно. Старые документы и JSON не обновляются от изменения центрального файла.

Чтение через `DOWNLOAD_URL` считается успешным только после реального CORS-запроса и проверки JSON. Ошибки авторизации, HTML входа и запрет CORS не скрываются. При необходимости используется сервер на том же HTTPS-хосте. Он принимает текущий OAuth-контекст SDK одним POST-запросом, не сохраняет токен и разрешает только настроенные домены. Публичные ссылки автоматически не создаются.

## Ограничения и приёмка

1. Реальные права приложения, ёмкость пользовательского поля, CORS портала, DOCX/PDF и автоматизация CRM проверяются после установки. Список `methods` не используется как основание для разрешения или запрета доступа. Генератор проверяется прямым вызовом списка шаблонов, права записи — при записи.
2. REST-запросы не образуют общую транзакцию. Состояние проверяется до и после записи, но полностью исключить одновременную серверную запись другого пользователя без отдельного серверного механизма нельзя.
3. Журнал предотвращения дублей принадлежит браузеру. Очистка localStorage или работа с другого компьютера требует сверки истории; безусловного глобального `exactly once` у REST нет.
4. При неоднозначном создании документа повтор блокируется до сверки. Если документ отсутствует либо портал не сохранил маркер, требуется ручное разбирательство; автоматическая повторная генерация не включается.
5. SHA-256 проверяет целостность, но не заменяет электронную подпись. Прокси при запрете CORS требует собственного HTTPS-хоста; ZIP-хостинг Bitrix24 не исполняет Node.js.
