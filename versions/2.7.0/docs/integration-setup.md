# Установка интеграции v2.7.0-integration.2

## Размещение и права

Обновляется существующее приложение Bitrix24. Второе приложение создавать не нужно. Сохраните резервную копию размещённых файлов и замените файлы приложения целиком. В ZIP `index.html` и `admin.html` находятся в корне. Регистрация `CRM_DEAL_DETAIL_TAB` и получение ID сделки сохранены; админка не регистрирует вкладку. Старые версии и DOCX-блок подписи сохранены в репозитории.

Открывайте административную панель по ссылке в настройках конструктора внутри iframe Bitrix24. Переход происходит в том же фрейме, сохраняя контекст SDK. Прямое открытие `admin.html` вне установленного приложения не предоставляет авторизацию.

Требуются HTTPS, современный браузер с Web Crypto и Web Locks, права приложения `crm`, `catalog`, `disk`, `placement`, `user_basic` и базовые методы приложения. Менеджеру нужны чтение/изменение выбранной сделки, чтение каталога и цен, чтение файлов текстов/подписей и создание документов. Администратору дополнительно нужны редактирование файла текстов и загрузка в выбранную папку. Уточните доступность REST и генератора документов на тарифе портала.

Общие настройки записываются только администратором: проверка `BX24.isAdmin()` в интерфейсе дополняет серверное ограничение `app.option.set`. Названия методов и ошибок попадают в диагностику без тел запросов и токенов.

## Первичная настройка

1. Загрузите `data/yuzm-quote-texts.json` в папку Диска Bitrix24. Сохраните ID файла и папки.
2. В настройках конструктора выберите существующий общий DOCX-шаблон КП. Существующая настройка `yuzmQuoteTemplateId` сохранена.
3. Откройте «Административная панель». Список полей загружается из `crm.deal.fields` и `crm.deal.userfield.list`. У каждого назначения видны название, код, тип, множественность и ID/названия вариантов списка.
4. Назначьте первичные поля: дата создания, клиент, ответственный, оплата, вид/адрес/дата доставки. По умолчанию используются только стандартные `DATE_CREATE`, `COMPANY_ID`, `ASSIGNED_BY_ID`; пользовательских ID в исходниках нет. При работе с физлицами выберите `CONTACT_ID` или совместимое поле связи. Необязательные назначения можно оставить пустыми; при необходимости отметьте их обязательными.
5. Назначьте существующие поля результатов: сумма заказа, стоимость доставки, масса, JSON последнего КП. Денежные результаты допускают типы `money`, `double`, `integer`; масса — `double`/`integer`; JSON — `string`. Дробный результат не округляется при записи в целочисленное поле, а блокирует сохранение с понятной ошибкой. Желательно использовать `double` достаточной точности.
6. Для множественного поля результат передаётся массивом с одним значением. Списки читаются по ID с сохранением отображаемых названий. Для подписи нужен ровно один ответственный сотрудник.
7. Укажите ID JSON-файла, папки и при необходимости справочных файлов. Можно показать список JSON-файлов выбранной папки. Настройте привязки подписей сотрудников по ID изображения; используется прежний ключ `yuzmManagerSignature_<ID>`.
8. Оставьте К2 коэффициентом доставки. К1 — скидка, К2 — доставка, К3 — покрытие или краска. Их подписи показаны у каждой строки. Другие назначения доставки доступны в настройках для расширения.
9. Укажите фактический допустимый размер JSON в байтах. Значение 60000 — консервативный лимит приложения, а не обещание ёмкости любого поля CRM. Дополнительно учитывается `MAX_LENGTH`, если портал возвращает его в метаданных. При превышении лимита документ и CRM не изменяются. Проверьте размер поля на своём портале; приложение его не создаёт и не расширяет.
10. Нажмите «Сохранить общие настройки». Эта кнопка проверяет структуру, обязательные значения, формат ID, существование/типы/назначения полей, записывает `app.option` и перечитывает результат. Она не обращается к `methods`, генератору или содержимому файлов Диска. Отдельно нажмите «Проверить конфигурацию»: результаты чтения полей, прямого вызова `crm.documentgenerator.template.list`, JSON, папки и дополнительных файлов показываются независимо. Ошибка диагностики не отменяет сохранение и не сбрасывает соответствия. Реальные права записи проверяются только при соответствующем действии.

Конфигурация хранится в `app.option` под ключом `yuzmIntegrationConfig`. DOCX-шаблон и подписи сохраняют прежние ключи в том же приложении. Тексты находятся на Диске; в `app.option` хранится только ID файла. Не выбирайте одно поле для двух параметров.

## Статус сохранения

При редактировании появляется «Есть несохранённые изменения». После подтверждённой записи — «Настройки сохранены» и время редакции; при ошибке контрольного чтения — «Запись отправлена, подтверждение сохранения не получено». Соответствия остаются в форме. Перечитывание с потерей изменений требует подтверждения. Если ключа ещё нет, показывается «Общие настройки ещё не сохранены». Менеджер может прочитать общие настройки, но не записывать их. [Подробности исправления](settings-save-fix.md).

## Чтение Диска и CORS

Приложение получает метаданные официальным `disk.file.get` и проверяет реальное чтение `DOWNLOAD_URL` через CORS без cookies. HTML страницы входа, закрытый CORS, неправильный JSON и ошибки авторизации не считаются успешной загрузкой. Публичная ссылка на файл автоматически не создаётся.

Если облачный портал не разрешает чтение из iframe, используйте поставляемый `server.mjs` на своём HTTPS-хосте. Встроенный ZIP-хостинг Bitrix24 не исполняет Node.js: для этого режима разместите ту же интеграцию на собственном хосте и укажите её HTTPS-обработчик, сохранив приложение и его настройки.

Пример запуска Node.js 20+ за HTTPS reverse proxy:

```sh
APP_ORIGIN=https://quote.example.ru \
BITRIX_ALLOWED_DOMAINS=yzm-krd.bitrix24.ru \
PORT=8080 node server.mjs
```

В админке установите путь `/api/disk-json`. Прокси использует текущий OAuth-токен из `BX24.getAuth()` только в памяти одного POST-запроса. Токен не сохраняется в `app.option`, localStorage, исходниках или логах. Не включайте журналирование тел запросов/авторизационных URL на reverse proxy. Сервер слушает только `127.0.0.1`; внешний HTTPS обеспечивает ваш веб-сервер.

Разрешены только заданные домены порталов. Если официальный URL скачивания перенаправляет на CDN, добавьте точное проверенное имя этого хоста через `BITRIX_DOWNLOAD_HOSTS` (список через запятую). Произвольные URL, HTTP и переходы на посторонние хосты запрещены. Для каждого портала проверяйте CORS или прокси на тестовой сделке: имитация API не подтверждает настройки реального облака.

## Расчёт, масса и доставка

Формула калькулятора сохранена:

```text
Цена единицы = (базовая цена + включённые метизы) × К1 × К2 × К3
Сумма строки = цена единицы × количество
Итого = сумма строк с выбранным прежним правилом округления
```

Масса не влияет на цену. При выборе товара масса единицы подставляется из уже читаемого свойства 112; её можно уточнить. Для старых строк и работ укажите массу явно, включая 0. Общая масса = сумма масс единицы × количество; единицы исходного справочника — килограммы.

Доставка, включённая коэффициентом К2, выделяется как разница между текущим итогом и штатным расчётом тех же изделий с К2 = 1. Так учитываются скидка К1, покрытие К3, количество и прежнее округление. К2 меньше 1 даёт отрицательную доставку и блокирует сохранение; используйте К1 для скидки.

Отдельная платная доставка добавляется произвольной строкой: отметьте «Отдельная доставка». Её сумма уже входит в товары и итог КП, масса равна 0, а полная сумма этой строки добавляется к выделенной доставке один раз. Отдельной невидимой надбавки к итогу нет.

CRM хранит округлённую цену единицы. Если выбранное округление суммы строки даёт иной итог, сохранение блокируется до выбора «Сначала цена единицы». Приложение не меняет правило округления автоматически.

## Документы и тексты

Категории `payment`, `delivery`, `fasteners`, `documents`, `validity` содержат стабильные `id`, подписи, фактический текст и `defaultPresetId`. `allowCustom: false` запрещает произвольный текст. Дополнительная категория задаётся в том же JSON с уникальным полем вида `Yuzm…Terms`; основные компоненты менять не требуется. Поле нужно добавить в DOCX-шаблон.

Новый локальный черновик получает действующие тексты. Существующий черновик сохраняет введённые формулировки. Кнопка перечитывания обновляет список вариантов, сохраняя ручной текст; выберите новый вариант явно. Публикация в админке использует `disk.file.uploadVersion`, затем повторно читает файл и проверяет содержимое. ID файла сохраняется. Кнопка создания нового файла загружает JSON в папку, после чего нужно сохранить общую конфигурацию.

В документ по-прежнему передаются существующие поля условий и подписи. Дополнительно доступны `YuzmOrderCreatedAt`, `YuzmClient`, `YuzmPaymentType`, `YuzmDeliveryType`, `YuzmDeliveryAddress`, `YuzmDeliveryDate` из выбранных первичных полей. Множественные значения отображаются через запятую; списки — по названиям. Это дополнительные значения для DOCX; структура существующего шаблона автоматически не меняется.

Фактически использованные тексты и версия текстовой конфигурации входят в JSON расчёта. Изменение центрального файла не обновляет старые JSON и документы.

## Сохранение, ошибки и восстановление

«Предпросмотр КП» и «Сохранить КП в сделку» открывают предпросмотр. Запись начинается только по «Сформировать и сохранить КП» и после подтверждения полной замены существующих товарных строк. Каталожные строки используют ID, произвольные — наименование с `productId = 0`. Создания товаров каталога нет.

Перед созданием документа проверяются сопоставления, первичные поля, валюта, активность каталожных товаров, сумма, масса, доставка, допустимый размер JSON и шаблон. После создания документа записываются товары, результаты и JSON. Затем всё перечитывается: успешным считается только подтверждённый полный результат.

Журнал последней операции хранится отдельно от локального черновика по порталу и ID сделки. При частичной ошибке кнопка «Продолжить сохранение КП» использует замороженный исходный расчёт, не заменяя текущий черновик и не создавая копию уже известного документа. Web Locks предотвращает одновременное сохранение одной сделки в разных вкладках того же браузера.

Если ответ на создание документа потерян или неоднозначен, автоматическое повторное создание блокируется. Найдите созданный документ в истории, нажмите «Проверить документ незавершённого сохранения» и введите ID. Проверяются сделка, шаблон и маркер операции в названии. Если документ не найден или портал не сохраняет маркер в названии, автоматическая разблокировка не выполняется: сначала требуется ручная сверка истории и журнала администратором. Удалять журнал вслепую нельзя.

API Bitrix24 не даёт транзакцию на весь сценарий или атомарное условное обновление сделки. Изменения другого пользователя проверяются до записи; оставшееся окно одновременной записи на стороне сервера полностью исключить невозможно. Автоматического отката старых товаров при ошибке нет, чтобы не затереть последующие чужие изменения. Частичное состояние показывается явно, документы не удаляются.

«Восстановить последний расчёт из сделки» читает только настроенное JSON-поле, проверяет схему/алгоритм, сделку, документ, SHA-256, тексты, товары и повторный расчёт. Перед заменой локального черновика запрашивается подтверждение. При открытии приложения этот JSON не применяется автоматически. SHA-256 обнаруживает повреждения; это не электронная подпись и не доказательство авторства.

Сохраняется один последний снимок со статусом `generated`. Поля согласования, стадии сделки, производство и спецификации приложение не меняет. Документы остаются в истории CRM. Действующие роботы портала — отдельная конфигурация, которую нужно проверить при приёмке.

## Проверки

Из корня репозитория: `npm test` и `npm run check` проверяют также v2.7.0. В распакованном приложении те же команды проверяют его собственные модули и тесты. Для браузерной проверки запустите HTTP-сервер на `127.0.0.1:8080`, затем `python3 tests/browser-integration.py`; нужны Playwright и Chromium. Тест использует исключительно имитацию API.

Для реальной приёмки используйте [протокол](acceptance-718.md).
